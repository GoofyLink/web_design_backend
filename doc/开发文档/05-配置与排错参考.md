# 配置与排错参考

本篇用于查询运行地址、排查常见问题，以及继续学习完整容器环境。端口以当前 YAML 和 Compose 配置为依据。

## 区分宿主机地址与容器地址

`127.0.0.1` 指向当前进程所在的网络环境。Windows 进程中的它指宿主机，容器中的它指该容器。

| 组件 | Windows 宿主机访问 | 同一 Compose 网络中的容器访问 |
| --- | --- | --- |
| MySQL | `127.0.0.1:33069` | `mysql:3306` |
| Redis | `127.0.0.1:36379` | `redis:6379` |
| Kafka | `localhost:9094` | `kafka:9092` |
| Nginx | `127.0.0.1:8888` | `nginx-gateway:8081` |
| Jaeger UI | `127.0.0.1:16686` | `jaeger:16686` |
| Elasticsearch | `127.0.0.1:9200` | `elasticsearch:9200` |
| Kibana | `127.0.0.1:5601` | `kibana:5601` |
| Prometheus | `127.0.0.1:9090` | `prometheus:9090` |
| Grafana | `127.0.0.1:3001` | `grafana:3000` |
| Asynqmon | `127.0.0.1:8980` | `asynqmon:8080` |

Kafka 地址按当前 `KAFKA_ADVERTISED_LISTENERS` 判断。即使端口映射可连接，客户端仍需要能够访问 broker 返回的地址；不要只根据旁边的旧注释选择端口。

## 查询用户 API

以下路径来自当前 `usercenter.api` 和 `routes.go`：

| 方法 | 完整路径 | JWT | 请求字段 |
| --- | --- | --- | --- |
| POST | `/usercenter/v1/user/register` | 不需要 | `mobile`、`password` |
| POST | `/usercenter/v1/user/login` | 不需要 | `mobile`、`password` |
| POST | `/usercenter/v1/user/detail` | 需要 | 空对象 `{}` |
| POST | `/usercenter/v1/user/wxMiniAuth` | 需要 | `code`、`iv`、`encryptedData` |

注册和登录返回 token 数据；详情返回 `data.userInfo`。练习章节新增的 `/service/info` 不属于原仓库接口。

## 排查启动和请求问题

按“进程是否运行 → 连接地址是否正确 → 配置和凭据是否一致 → 业务数据是否满足条件”的顺序排查。

| 现象 | 优先检查 | 处理方式 |
| --- | --- | --- |
| 找不到 `dockerDesktopLinuxEngine` | Docker Desktop 引擎状态 | 启动 Docker Desktop，等待 `docker version` 能显示 Server |
| 端口占用或 bind 失败 | 是否启动了第二套进程 | 停止重复进程，或同时调整服务监听与调用方地址 |
| `lookup mysql` 或 `lookup redis` 失败 | 宿主机是否使用容器服务名 | 按入门配置改用宿主机映射端口 |
| MySQL `Access denied` | 用户、密码、授权来源 | 检查实际数据库账号；Compose 环境变量不会重置已有数据库密码 |
| `Unknown database` / 表不存在 | 是否创建库并执行了 SQL | 在新练习库导入用户中心脚本，确认两张表存在 |
| Redis `NOAUTH` / `WRONGPASS` | `Redis` 和 `Cache` 两处密码 | 与 Redis 的实际 `requirepass` 保持一致 |
| RPC `Unavailable` / connection refused | RPC 进程及 `Endpoints` | 先确认 `2004` 监听，再检查 API 的连接配置 |
| API 启动成功但调用 RPC 失败 | `NonBlock` 非阻塞初始化 | 查看 RPC 终端错误；API 启动不代表其依赖就绪 |
| 注册失败，提示已注册 | 手机号是否已存在 | 直接登录已有账号，不要重导 SQL 清库 |
| 登录成功，详情 401 | Bearer 格式、过期时间、签名密钥 | 重新登录，核对 API 与 RPC 的 `AccessSecret` |
| 详情返回 404 或 405 | 路径前缀与 HTTP 方法 | 使用 `POST /usercenter/v1/user/detail` |
| 日志持续报 Jaeger 连接错误 | 本地配置是否保留了 `Telemetry` | 入门时省略整个配置块；启用追踪时填写可达地址 |
| 新增 API 后返回 404 | 是否生成路由并重启进程 | 检查 `routes.go`，停止旧 API 后重新启动 |
| 生成后缺少 `Trans` 或方法签名冲突 | 是否使用了项目模板 | 检查 `--home` 指向的版本和生成差异 |
| PowerShell 的 HTTP 命令报错 | HTTP 状态码与响应体 | 400/401 本身会导致 `Invoke-RestMethod` 报错，不一定是网络失败 |

查看本地监听端口：

```powershell
Get-NetTCPConnection -State Listen | Where-Object LocalPort -In 1004,2004,4008,4009,33069,36379
```

检查数据库容器日志：

```powershell
Set-Location E:\go\go-zero-looklook-main
docker compose -f docker-compose-env.yml logs --tail 100 mysql redis
```

本地 Go 进程的错误在启动它的 PowerShell 终端中；`docker logs looklook` 只适用于容器内运行的业务。

## 继续学习完整容器环境

完整环境包含较多组件。先完成用户中心，再逐项加入民宿、订单、队列和支付。原教程的入口为 [开发环境搭建](E:/go/go-zero-looklook-main/doc/chinese/01-开发环境搭建.md)，但需要先处理这些差异：

1. **统一 Compose 网络配置。** 两个 Compose 文件都声明 `looklook_net`，但子网分别为 `172.16.0.0/16` 与 `172.20.0.0/16`。在本地副本中统一网络方案和项目名，并检查已存在网络；不要把“依次执行两条 up 命令”当成已经验证的完整启动方案。Docker 网络创建后不能简单原地修改子网。
2. **初始化业务库。** 四个 SQL 文件分别对应 `looklook_usercenter`、`looklook_travel`、`looklook_order`、`looklook_payment`。原配置使用 root 从其他容器连接 MySQL，需确认实际授权，或给各业务配置专用账号。
3. **检查进程布局。** 默认 `modd.conf` 将多个 API、RPC 和任务进程放在同一 `looklook` 容器中，因此它们可以使用 `127.0.0.1` 互相连接。如果拆成独立容器，RPC 地址必须改为相应容器服务名。
4. **准备 Kafka topic。** 业务状态 topic 是 `payment-update-paystatus-topic`，日志 topic 是 `looklook-log`。当前 Kafka 使用 KRaft 配置，不需要照抄旧的 ZooKeeper 命令。
5. **配置微信能力。** 小程序授权和支付需要实际的 AppID、商户信息、私钥、API v3 密钥及可达的回调地址。仓库示例值不足以完成真实支付。
6. **逐项检查就绪状态。** Compose `depends_on` 的普通依赖关系不等于数据库或消息队列已经就绪；根据日志和实际请求确认服务。

当 Kafka 容器已启动并就绪后，可以在宿主机创建和检查 topic：

```powershell
docker exec kafka /opt/kafka/bin/kafka-topics.sh --create --if-not-exists --bootstrap-server localhost:9094 --replication-factor 1 --partitions 1 --topic payment-update-paystatus-topic
docker exec kafka /opt/kafka/bin/kafka-topics.sh --create --if-not-exists --bootstrap-server localhost:9094 --replication-factor 1 --partitions 1 --topic looklook-log
docker exec kafka /opt/kafka/bin/kafka-topics.sh --list --bootstrap-server localhost:9094
```

`modd.conf` 监视的是各服务指定目录下的 Go 文件。修改 YAML、共享 `pkg` 或 Model 后，不要假定一定自动重启，应检查规则并主动重启受影响进程。

## 区分日志、指标与追踪

| 能力 | 回答的问题 | 项目中的链路 |
| --- | --- | --- |
| 日志 | 哪个请求或步骤报了什么错误？ | 应用 → Filebeat → Kafka → go-stash → Elasticsearch → Kibana |
| 指标 | 最近请求量、延迟、错误率如何？ | 应用 `/metrics` → Prometheus → Grafana |
| 链路追踪 | 一次请求经过哪些服务，各自耗时多少？ | API/RPC 的 Telemetry → Jaeger |

宿主机运行的 Go 控制台日志不会自动进入面向 Docker 容器日志目录的 Filebeat 采集配置。容器中的 Prometheus 若要采集宿主机进程，也需要调整采集目标；默认的 `looklook:4008` 对应容器模式。
