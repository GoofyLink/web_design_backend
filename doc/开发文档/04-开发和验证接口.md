# 开发和验证接口

本篇先添加一个无需数据库的新接口，练习“修改定义 → 生成代码 → 实现 logic → 验证请求”。随后说明扩展 RPC 与 Model 的方式。

以下操作是学习步骤，不代表仓库已添加该练习接口。修改前保留可恢复的源码副本；如果项目已由 Git 管理，可建立学习分支并查看生成前后的差异。

## 准备代码生成工具

先安装与仓库模板匹配的 goctl 1.7.3：

```powershell
go install github.com/zeromicro/go-zero/tools/goctl@v1.7.3
goctl --version
```

如果提示找不到 `goctl`，通过 `go env GOPATH` 和 `go env GOBIN` 确定工具安装位置，把对应目录加入 `PATH` 后重新打开终端。默认通常是 `GOPATH/bin`；设置了 `GOBIN` 时以该值为准。

本节仅生成 API，不需要 protobuf 工具。扩展 RPC 时再准备 protoc、protoc-gen-go 和 protoc-gen-go-grpc。

## 使用项目模板

项目生成的 handler 调用 `pkg/result`，Model 也包含事务等自定义方法。直接使用默认模板重新生成，可能与现有调用方式不匹配。

1. 在项目根目录展开已有模板：

   ```powershell
   Set-Location E:\go\go-zero-looklook-main
   Expand-Archive -LiteralPath .\deploy\goctl\1.7.3.zip -DestinationPath .\data\goctl-templates
   Get-ChildItem .\data\goctl-templates\1.7.3
   ```

   预期可见 `api`、`rpc`、`model` 等目录。若目标目录已存在，先检查是否已有相同模板，不必重复解压覆盖自己的修改。

2. 保存模板绝对路径，供本终端后续命令使用：

   ```powershell
   $templatePath = (Resolve-Path .\data\goctl-templates\1.7.3).Path
   ```

   `--home` 应指向直接包含 `api`、`rpc`、`model` 的目录，不是 zip 文件，也不是它们的上一级。

## 添加服务信息接口

练习目标是添加 `GET /usercenter/v1/service/info`，返回服务名。该接口是学习用信息接口，不检查数据库、Redis 或 RPC 的就绪状态。

1. 在 [user.api](E:/go/go-zero-looklook-main/app/usercenter/cmd/api/desc/user/user.api) 末尾添加响应类型：

   ```go
   type ServiceInfoResp {
       Name string `json:"name"`
   }
   ```

2. 在 [usercenter.api](E:/go/go-zero-looklook-main/app/usercenter/cmd/api/desc/usercenter.api) 中找到不带 `jwt: JwtAuth` 的第一个 `service usercenter` 块，添加路由：

   ```go
   @doc "查询服务名称"
   @handler serviceInfo
   get /service/info returns (ServiceInfoResp)
   ```

   保留已有 `prefix: usercenter/v1` 和 `group: user`。不要把这段定义写入生成的 `routes.go`。

3. 在保存了 `$templatePath` 的 PowerShell 终端生成 API 代码：

   ```powershell
   Set-Location E:\go\go-zero-looklook-main\app\usercenter\cmd\api\desc
   goctl api go -api usercenter.api -dir .. --style goZero --home $templatePath
   ```

   预期增加 `serviceInfoHandler.go`、`serviceInfoLogic.go`，并更新路由与类型。生成器通常保留已有 logic，但仍需检查所有生成差异，特别是自定义 handler、配置和入口。

4. 打开新生成的 `app/usercenter/cmd/api/internal/logic/user/serviceInfoLogic.go`，保留生成的结构体、构造函数和方法签名，将方法内的占位实现替换为：

   ```go
   return &types.ServiceInfoResp{
       Name: "usercenter-api",
   }, nil
   ```

   如果生成的 import 中尚无 `types`，添加 `looklook/app/usercenter/cmd/api/internal/types`。不要把整个文件替换成只有 `return` 的片段。

5. 在项目根目录格式化并编译 API：

   ```powershell
   Set-Location E:\go\go-zero-looklook-main
   gofmt -w .\app\usercenter\cmd\api\internal\logic\user\serviceInfoLogic.go
   go build ./app/usercenter/cmd/api/...
   ```

   无错误退出表示编译通过。编译不等于接口已运行。

6. 停止旧 API 进程，再按入门教程使用本地配置启动 API。在另一个终端验证新接口：

   ```powershell
   Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:1004/usercenter/v1/service/info' | ConvertTo-Json -Depth 5
   ```

   使用项目模板时，预期响应为：

   ```json
   {
     "code": 200,
     "msg": "OK",
     "data": {
       "name": "usercenter-api"
     }
   }
   ```

7. 再次验证原有登录和用户详情接口，确认新增路由没有改变已有行为。如果新接口缺少 `code/msg/data`，检查生成的 handler 是否调用了 `result.HttpResult`。

## 扩展 RPC 接口

当业务需要被其他服务复用时，在 RPC 层提供方法。不要为了每个简单 HTTP 返回都新增 RPC。

1. 准备 protoc，并确认 `protoc --version` 可用。仓库生成脚本要求 protoc 至少为 3.13.0。
2. 安装 Go 代码生成插件。以下是与仓库依赖时代相近的固定版本示例；更换工具版本后检查生成差异：

   ```powershell
   go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.35.1
   go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.3.0
   protoc-gen-go --version
   protoc-gen-go-grpc --version
   ```

3. 在 [usercenter.proto](E:/go/go-zero-looklook-main/app/usercenter/cmd/rpc/pb/usercenter.proto) 中定义请求、响应和 RPC 方法。为新字段分配新编号，不要重用已有字段编号；删除字段时考虑使用 `reserved` 保留编号。
4. 在同一个 PowerShell 终端中生成代码。若重开过终端，先重新设置模板路径：

   ```powershell
   $templatePath = 'E:\go\go-zero-looklook-main\data\goctl-templates\1.7.3'
   Set-Location E:\go\go-zero-looklook-main\app\usercenter\cmd\rpc\pb
   goctl rpc protoc usercenter.proto --go_out=.. --go-grpc_out=.. --zrpc_out=.. --style goZero --home $templatePath
   ```

5. 在新增的 RPC logic 中实现业务，通过 `svcCtx` 使用 Model 或其他 RPC。API logic 再调用生成的客户端方法。
6. 编译相关 API 和 RPC；重启相关进程，用真实请求验证成功、输入错误和权限失败的情况。

不要手工修改 `.pb.go` 文件。旧教程删除 `omitempty` 的 `sed` 命令不是运行项目的前置步骤；API 对外 JSON 应优先通过 `.api` 类型明确约定。

## 扩展数据库访问

新增字段或表时，先明确 SQL 变更，再生成 Model。仓库初始化 SQL 用于搭建示例数据库，不能直接当作保留业务数据的迁移脚本。

建议把 Model 先生成到临时目录，对比后再合入对应服务。以现有用户中心表结构为例：

```powershell
Set-Location E:\go\go-zero-looklook-main
$templatePath = (Resolve-Path .\data\goctl-templates\1.7.3).Path
goctl model mysql ddl -src ./deploy/sql/looklook_usercenter.sql -dir ./data/generated-usercenter-model -c --style goZero --home $templatePath
```

这条命令从 DDL 生成代码，不会把 SQL 导入数据库。检查生成的包名、缓存键、事务方法和 `Insert(ctx, session, ...)` 等方法签名，再决定如何合入。自定义查询放在非 `_gen.go` 的扩展文件中。

现有 [genModel.sh](E:/go/go-zero-looklook-main/deploy/script/mysql/genModel.sh) 通过数据库反向生成代码，属于 Bash 脚本。PowerShell 不能直接按 Bash 语法执行；使用前还要调整其连接账号和输出目录。

## 验证实际业务变更

验证范围应覆盖本次修改，而不是只确认编译成功：

| 修改类型 | 最少需要确认的行为 |
| --- | --- |
| 新增公开接口 | 路径和方法正确，字段符合定义，旧接口仍可用 |
| 修改鉴权 | 无 token 被拒绝，有效 token 可访问，不能读取别人的数据 |
| 修改事务 | 成功时全部写入，失败时不留下部分数据 |
| 修改缓存 | 更新后能读到新值，缓存故障不会被误判为数据不存在 |
| 修改消息消费 | 重复消息不重复执行关键业务，失败会按预期重试 |

包含业务规则的变更适合补充单元测试，依赖 MySQL、Redis 或 RPC 的行为还需要集成验证。仓库中的 `go test ./...` 不能替代上述业务请求验证。
